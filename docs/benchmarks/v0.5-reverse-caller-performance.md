# v0.5 Reverse-Caller Performance Evidence

This artifact records the #342 baseline and the frozen adoption rule before any
candidate source edit. It measures the normal ProjectAtlas scanner followed by
the public `projectatlas --format json summary src/target.rs --limit 500`
boundary, which owns `load_import_relations_for_symbols -> import_alias_map ->
called_by_map`. Each fresh CLI process was sampled seven times on Windows
(x86_64-pc-windows-msvc, debug build from the exact base below).

## Frozen adoption rule

Adopt exactly one smallest shared service/database candidate only when its
median wall time improves by at least 20% on both the high-import and
representative-large fixtures, while median wall time regresses by no more than
5% on small, high-symbol, and duplicate-alias fixtures. It must also preserve
semantic truth, exact Rust/TypeScript/Python alias and ambiguity behavior,
per-target fairness, deterministic ordering/truncation, freshness,
cancellation, all-or-error decoding, import-alias statement/row/byte bounds,
SQLite plan ownership, and encoded output bytes. Otherwise retain the current
implementation and publish reproducible no-change evidence.

The one candidate selected for comparison is parsing each persisted import
relation once and reusing those parsed references across displayed symbols in
the existing service-side matching loop. It changes no SQL, schema, index,
limit, alias rule, or public/helper signature.

## Baseline identity and method

- Base: `fcca45c18f3ff9251ceafb757f8e76194e3d20e0`
- Harness: [`docs/benchmarks/harness/reverse_caller.py`](harness/reverse_caller.py);
  rerun from the repository root with `python
  docs/benchmarks/harness/reverse_caller.py --binary
  .target/debug/projectatlas.exe --repeats 7` (use the platform’s built CLI
  path on other hosts).
- Workload: generated minimal Rust repositories with one `src/target.rs`
  summary target and real Tree-sitter scanning; no fixture binary and no
  process-global test environment.
- Shapes: small (4 target symbols, 1 caller), high-symbol (320 symbols, 1
  caller), high-import (1 symbol, 240 callers), duplicate-alias (1 symbol and
  two same-name imports in one caller), representative-large (120 symbols,
  120 callers).
- Repeats: 7 fresh summary processes per shape after one normal `init --no-scan`
  and `scan`.
- Wall/CPU: `perf_counter` and child process CPU time sampled with psutil.
  RSS: maximum sampled child working set. These are closest reliable existing
  process measurements on this Windows host and include process startup.
- Allocation proxy: exact UTF-8 bytes owned by the bounded import relation
  fields returned by the two import-alias reads; no allocator instrumentation
  or new dependency was introduced.
- Encoded output: exact bytes emitted by the JSON summary process.
- Import-alias SQL statements: one bounded matching-term statement plus one
  exact-path statement for every distinct caller path returned by the matching
  read. Rows and relation bytes are the exact returned rows and their path,
  source, target, and line-field byte proxy.
- Query plan: the current matching read uses the existing covering index:
  `SEARCH symbol_relations USING COVERING INDEX
  idx_symbol_import_alias_lookup (kind=?)`.
  The exact caller-path read uses the same covering index with
  `SEARCH symbol_relations USING COVERING INDEX
  idx_symbol_import_alias_lookup (kind=? AND path=?)`.

## Candidate comparison and decision

The candidate passed the existing Rust/TypeScript/Python alias and ambiguity
tests, and its output, import-alias SQL statements, rows, relation-byte proxy,
and query plan were identical to baseline on every shape. Candidate medians:

| Shape | Candidate wall ms | Candidate CPU ms | Peak RSS bytes | Encoded output bytes | Wall change vs baseline |
| --- | ---: | ---: | ---: | ---: | ---: |
| small | 204.31 | 171.88 | 23,363,584 | 2,543 | -0.59% |
| high-symbol | 251.12 | 203.12 | 25,276,416 | 85,473 | -4.47% |
| high-import | 232.08 | 187.50 | 24,551,424 | 2,497 | -0.27% |
| duplicate-alias | 201.06 | 156.25 | 23,257,088 | 1,683 | -2.60% |
| representative-large | 419.98 | 390.62 | 24,936,448 | 38,050 | -32.56% |

The candidate is not adopted. It materially improves the representative-large
shape and stays within the small/high-symbol/duplicate-alias regression bound,
but it does not improve the high-import shape by the required 20% (the measured
change is -0.27%). The frozen rule therefore retains the current implementation
with this reproducible no-product-change result. The service-side parser reuse
candidate was reverted after comparison; no product SQL, schema, index, or
runtime behavior changed.

## Architecture reconciliation

The reverse-caller ownership remains the existing service/database boundary
shown in [`docs/v050-release-architecture.md`](../v050-release-architecture.md#reverse-caller-query-and-decision-boundary):
the service selects bounded alias terms and performs exact semantic matching;
the database owns prepared, indexed, bounded relation reads; and the summary
adapter owns deterministic caller projection. Because the measured candidate
was rejected and no ownership or communication flow changed, the existing
Mermaid view needs no update.

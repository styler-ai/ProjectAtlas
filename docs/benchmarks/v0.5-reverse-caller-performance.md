# v0.5 Reverse-Caller Performance Evidence

This is the reproducible, evidence-only record for ProjectAtlas #342. The
decision is still **retain current implementation; no product change**. The
candidate was compared through the public JSON `summary` command and did not
meet the frozen adoption rule.

## Frozen decision rule

Adopt the candidate only when its median wall time improves by at least 20% on
both `high-import` and `representative-large`, regresses by no more than 5% on
`small`, `high-symbol`, and `duplicate-alias`, and preserves all observable
semantics. The semantic gate covers encoded output bytes, status/errors,
caller lists and ordering/truncation, exact identity and alias behavior across
Rust/TypeScript/Python, ambiguity rejection, freshness, and bounded query
behavior. The rule and thresholds were not moved for this amendment.

The immutable candidate is the exact LF patch in
[`reverse-caller-candidate.patch`](reverse-caller-candidate.patch). It parses
each persisted import relation once and reuses those parser-owned references
across displayed symbols in the existing service loop. It changes no product
SQL, schema, index, limit, alias rule, public signature, or runtime default.
The patch is retained so both implementations can be rebuilt rather than
treated as an opaque binary. The harness exports the exact baseline revision
and runs `git apply --check --unidiff-zero --whitespace=nowarn` against that
source before it accepts any benchmark input.

## Workload and semantic coverage

Each arm creates a fresh isolated repository, runs the real
`projectatlas init --no-scan` and `projectatlas scan`, then invokes the public
`projectatlas --format json summary <target> --limit <n>` boundary in a fresh
process. Every fixture contains native Rust, TypeScript, and Python targets and
callers. The caller aliases are language-qualified so the existing per-target
caller bound does not select an unrelated language's relation.

| Shape | Target symbols | Callers per language | Additional behavior |
| --- | ---: | ---: | --- |
| `small` | 4 | 1 | baseline semantic smoke |
| `high-symbol` | 320 | 1 | symbol/output growth |
| `high-import` | 1 | 240 | import-query and caller-path pressure |
| `duplicate-alias` | 1 | 1 | two same-name imports in one caller; must omit the caller |
| `representative-large` | 120 | 120 | combined symbol/import pressure |

The first target is summarized with limits 1 and 500 to prove truncation; all
other targets use 500. Expected caller lists are compared exactly after the
production 20-caller cap and deterministic path ordering. The duplicate-alias
fixture asserts that an ambiguous local alias produces no caller. A separate
Python multi-binding fixture runs with summary limit 1 and proves that
`from package.py_target import a as shared, b as shared` retains the caller for
the displayed `a` symbol: repeated local names within one stored relation are
deduplicated, while the existing separate-relation ambiguity remains rejected.

The same public boundary also records three bounded negative/compatibility
cases for each arm: a missing summary path must return the same error, one
admitted `calls` relation has its decoded `line` value changed to a malformed
SQLite value and must fail with a nonzero status and no partial JSON, and a
target source is changed after scanning and must still produce the same
live-source summary. Raw stdout/stderr, return status, and decoded summary come
from ordinary release binaries. Each failure is replayed untimed with the
matching evidence binary, and its engine-bound query observations are compared
between arms, including exact failure behavior for the malformed relation.

Cancellation is exercised through the existing MCP request boundary rather
than by killing a process: each arm starts its real `mcp` server, sends an
`atlas_file_summary` request for a bounded 10,000-symbol fixture, sends the
standard `notifications/cancelled` notification for that request, and waits
for the existing `RequestContext`/`IndexWorkControl` bridge to report a
terminal canceled result before sending a `ping`. The request response must
be suppressed, the server must remain alive for the ping, no partial
`file_summary` payload may be emitted, and the baseline/candidate process
status plus complete stdout/stderr streams must match. The terminal marker is
feature-gated benchmark evidence at that bridge only; it does not add a
cancellation API or change the default runtime. A bridge-drop marker is
diagnostic only and cannot satisfy the cancellation proof: accepted evidence
must report the authoritative canceled operation result.

## Production query evidence

The benchmark observer is a narrow, feature-gated hook at the existing
`projectatlas-db` query owners, enabled only by the CLI's
`reverse-caller-benchmark` feature. It writes no database state and is absent
from the ordinary release binaries used for timing. It does not enable
`rusqlite/trace` or add a tracing framework. Query capture is also inactive in
a feature build until the trace operation explicitly starts it.

For the exact production SQL calls, the observer records:

- each deduplicated import-target matching statement and binding;
- each exact caller-path statement for the distinct paths returned by that
  matching read; and
- the single bounded call-target statement.

Every event retains sequence, query family, binding, exact production SQL and
bindings, bound limit, decoded row count, UTF-8 bytes in the returned relation
fields, typed success or failure outcome, and the exact `EXPLAIN QUERY PLAN`
details. A failed call-target row decode records the propagated database error
and zero accepted rows before the same all-or-error result leaves the storage
boundary. Timed wall/CPU/RSS/output
samples use separate ordinary release binaries compiled without
`reverse-caller-benchmark`; they therefore contain neither the query observer
nor the global counting allocator. The harness runs one separate untimed
feature-binary allocation-only replay and one trace/query-plan replay per
target/limit, and compares both decoded summaries with the final timed sample.
Query capture stays inactive during the allocation-only replay, so its vector,
SQL/binding clones, and row-byte accounting do not enter allocation totals.
Replay wall/CPU/RSS values are not adoption metrics.

The production `AtlasStore::connection` prepares each exact captured SQL as
`EXPLAIN QUERY PLAN` and binds the captured `rusqlite::Value` values on that
same connection. Each trace records the bundled SQLite version, numeric
version, compile options, and the stable
`projectatlas-db::AtlasStore::connection` provenance. No Python `sqlite3`
connection or synthetic `LIKE`/`IN` query participates in plan evidence. The
byte value is an explicit bounded relation row-byte proxy (field bytes plus
the stored line-width), not a fabricated allocation count. In each separate
benchmark-feature evidence binary, a standard-library `System` allocator
wrapper records successful allocation, reallocation, and deallocation
calls/bytes during the allocation-only replay. Counters reset immediately before
`build_file_summary_from_source_with_selection`; the snapshot is captured in
a local immediately after it returns and before trace JSON is written. These
are allocator requests from the untimed evidence replay, not from the ordinary
timing process; they exclude setup/serialization and are not RSS, OS heap
commitment, allocator arena overhead, or relation-field bytes. Timed process
wall time, child CPU time, peak sampled RSS, and exact encoded stdout/stderr
bytes come only from the ordinary release binaries.
The ignored full result is the raw per-run record, while the tracked result is
the bounded review projection of its aggregate and selected evidence; no
synthetic `LIKE`/`IN` replacement query is used.

## Measured result

The three-repeat release-profile artifact
(`projectatlas.reverse-caller-performance.v8`) was generated from pinned source
revision
`0243d5c6da0e66210abbe1c95b2815d651a77c2d` with the benchmark-only observer
amendment applied equally to baseline and candidate; only the retained
candidate patch differs in product code. It records zero semantic findings and
the following median wall-time changes for candidate versus baseline. It also
retains allocation call/byte medians from the separate untimed evidence
replays; every ordinary-binary timed invocation records no instrumentation:

| Shape | Baseline wall ms | Candidate wall ms | Change | Frozen bound |
| --- | ---: | ---: | ---: | --- |
| `small` | 112.39 | 113.14 | +0.66% | max +5% |
| `high-symbol` | 130.51 | 133.28 | +2.12% | max +5% |
| `high-import` | 134.25 | 132.67 | -1.17% | min -20% |
| `duplicate-alias` | 114.73 | 114.14 | -0.51% | max +5% |
| `representative-large` | 230.52 | 222.22 | -3.60% | min -20% |

The candidate therefore fails the unchanged performance gate: `high-import`
improves by only 1.17% and `representative-large` by only 3.60%, rather than
improving by the required 20% on each. `small`, `high-symbol`, and
`duplicate-alias` remain within their bounds.

All semantic cases—including the Python multi-binding relation—match exactly,
and untimed allocation totals are retained in the artifact. The amended
evidence does not justify a product change, so the current implementation
remains in place with no SQL, schema, index, runtime, or cache change.

The compact artifact records harness SHA-256
`9d695dedce54e77fd3a93caae844d5e7c7fb82f916ad81af13fd7ac874b10f60` and the
ignored full-result SHA-256
`c8dd9c2e6824047faa27c2d5a433097e9f9aadecea0e29fcd5cde2458c9432e8` over
18,687,631 bytes.

The tracked
[`v0.5-reverse-caller-performance-results.json`](v0.5-reverse-caller-performance-results.json)
is the compact review artifact. The complete raw result is intentionally kept
only in the ignored path recorded under its `reproduction.raw_trace_path`,
with its byte count and SHA-256 digest, and can be regenerated with the
existing harness command above.

## Architecture reconciliation

The ownership boundary is unchanged: the service selects bounded alias terms
and performs exact semantic matching; `projectatlas-db` owns prepared,
indexed, bounded relation reads; and the summary adapter owns deterministic
caller projection. The observer reports those existing owners only for this
benchmark build. Because the candidate was rejected and no communication or
ownership flow changed, the existing reverse-caller architecture diagram
remains truthful and needs no update.

# 0.5.1 indexing reference and targets

These targets were fixed before production changes for #708. This is a focused
Linux reference, not the complete installed release/platform acceptance.

## Reference

Use the published, checksum-verified optimized 0.5.0 Linux x64 archive, normal
telemetry, and a local filesystem accepted by the runtime's SQLite profile.
Do not benchmark the development binary or place a WAL database on unsupported
temporary filesystems. Each sample starts a fresh CLI process. Filesystem and
OS page caches remain warm; these are cold-process results, not cold-disk claims.
The workspace baseline passed locked all-target/all-feature `cargo check`.

Asset: `projectatlas-v0.5.0-x86_64-unknown-linux-gnu.tar.gz`, SHA-256
`745db48c00d5dbac2d245284219610582293e9d048949f608a3b4988228b7266`.
Reference host: Ryzen 7 5700U (8 cores / 16 logical CPUs), Linux
7.0.0-38-generic, local ext4. Rerun comparisons on the same host and storage.

The non-Git fixture contains 1,024 Rust files in 16 groups and one Markdown file,
with 746,554 initial source bytes. Each Rust file contains:

```python
"//! Generated indexing reference fixture.\n" + "".join(
    f"pub fn item_{i}_{j}(n: u64) -> u64 {{ n.saturating_add({j}) }}\n"
    for j in range(12)
)
```

File names are `src/group_{i//64}/module_{i}.rs`. The Markdown source links to
`src/group_0/module_0.rs`. Run `init`, `scan`, `symbols build`, and two
`watch --once` no-ops, then append one distinct exported function to module 0
and measure another `watch --once`. Repeat three times; subsequent first steps
are scans. Two additional initial samples use fresh unindexed copies of the
final source fixture (including the three tiny added functions). Record elapsed
time around the entire process and GNU time peak RSS; retain JSON reports to
confirm parsed/indexed counts. This reference supplies targets, not broad parser
or high-degree-graph coverage.

The three rounds yield one initial sample and five full scans: one explicit
scan per round plus two replacement first steps. The fresh copies add the
remaining two initial samples.

restages all 1,027 texts in 0.5.0. Later samples contain the appended functions.

## Targets and architecture decision

- Initial/full/rebuild each improve median latency and corresponding throughput
  by at least 10% on this reference, with complete required parsing/projection
  work. Maximum RSS may not exceed its baseline by more than 10%.
- Cold sparse refresh improves median latency by at least 50%, parses only
  changed source and genuinely affected dependencies, and preserves complete
  results and authored state. Dense changes and wider invalidation retain exact
  fallback under the existing resource limits.
- Cold unchanged refresh stays below 60 ms median on this reference and has no
  new publication or parse work. It uses one exact discovery and an ordered
  source-only database comparison. A fresh process has no trustworthy offline
  event history; it must inspect source bytes, including same-metadata edits.
  The measured discovery cost is acceptable, so no retained-history service is
  proposed.
- A continuously observed unchanged MCP refresh performs zero traversal,
  hashing, full-node decoding, parsing, or publication. Observation must retain
  root/policy/generation and event continuity; uncertainty selects exact work.
- Final acceptance must register named unaffected-navigation and supported-upgrade
  baselines before comparing them; their median latency and peak RSS may each
  increase by at most 10%. Those cases are not measured by this reference.
  Failure, cancellation, source races, writer races, and rollback
  retain identity, approved purposes, and the last complete publication.

Use the existing concrete refresh and RAII publication owners. Compare ordered
source fields without joining or decoding purpose/summary state. Feed discovered
changes through the existing dependency-aware incremental owner. Capture and
reuse source evidence within one operation; retain exact publication validation
until an equivalent source/writer witness is proven. No schema, new pool, tuning
pragma, daemon, or independent indexing framework is justified by this reference.

For continuously observed MCP refresh, reuse the server's existing
`SourceObservationRegistry::with_verified_read` to admit an epoch-bound no-op;
its exact/delta-repair route already owns writer-safe small-change reconciliation.
Full/policy/continuity uncertainty returns to the mutable shared refresh owner
under the same operation deadline. Raw event queues cannot authorize an update.
The normal-read repair cap remains independent of explicit refresh: large event
sets or dependency closures must select exact full work, never a truncated delta.

Keep work-count checks independent of time measurements. The complete release
matrix must additionally cover larger file/byte counts, dense graphs, supported
parser/document cases, warm MCP, arbitrary mixed changes, lost/offline events,
policy invalidation, plain directories, concurrency, upgrade and rollback on
Linux x64, Windows x64, macOS Intel and Apple Silicon. These boundaries have not
yet passed; this document makes no optimized-result claim.

## First implementation slice

The first optimized Linux probe uses the same fixture and normal telemetry,
three samples per indexing/change path and six cold-process no-op samples.
The local probe binary SHA-256 is
`f0954f44fd7f59f0660e6e0630b315440688b7a8a3c0ec2f76725127cda2bb95`.
It is a development build, not a published RC. The tiny appended functions
remain in subsequent fixture copies, as in the baseline procedure.

| Operation | Min / median / max seconds | Maximum RSS KiB | Median latency reduction |
| --- | --- | ---: | ---: |
| Initial index | 3.747 / 3.770 / 3.788 | 170224 | 28.3% |
| Full scan | 5.352 / 5.373 / 5.521 | 171396 | 22.4% |
| Explicit symbol/graph rebuild | 5.016 / 5.039 / 5.117 | 169800 | 23.5% |
| Cold-process unchanged refresh | 0.0429 / 0.0438 / 0.0448 | 19016 | 6.6% |
| Cold-process one-file edit | 0.141 / 0.144 / 0.149 | 24208 | 97.8% |

Initial/full/rebuild still parse all 1,025 symbol candidates with zero unchanged
candidates; initial/full stage all 1,027 admitted texts. No-op performs no parse
or publication. Sparse refresh stages/parses the one changed file; the shared
dependency-aware owner retains the remaining valid projections. These results
meet this reference's initial/full/rebuild, cold no-op, sparse and RSS targets.
They do not establish the larger-fixture or four-platform release matrix.

The full-build change reuses the existing storage-owned bulk-index policy:
capture exact non-unique derived read-index definitions, delete the prior graph
while its cascade lookup indexes remain available, drop those read indexes,
insert the complete graph, and rebuild the captured definitions once. Constraints
remain active. The existing atomic savepoint restores rows and indexes together
on failure. Both in-memory and spilled full publication use this order.

A prior per-file symbol batching experiment showed only about 1.7% difference
in paired full-scan runs. It was removed rather than retained as an unproven
optimization. A diagnostic trace located most baseline write calls in SQLite
temporary journal and WAL files; no cache-size or durability setting was weakened.

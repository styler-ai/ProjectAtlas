# 0.5.1 indexing reference and targets

These targets were fixed before production changes for #708. This is a focused
Linux reference, not the complete installed release/platform acceptance.

## Reference

Use the published, checksum-verified optimized 0.5.0 Linux x64 archive, normal
telemetry, and a local filesystem accepted by the runtime's SQLite profile.
Do not benchmark the development binary or place a WAL database on unsupported
temporary filesystems. Each sample starts a fresh CLI process. Filesystem and
OS page caches remain warm; these are cold-process results, not cold-disk claims.
The workspace baseline passed locked all-target/all-feature `cargo check`.

Asset: `projectatlas-v0.5.0-x86_64-unknown-linux-gnu.tar.gz`, SHA-256
`745db48c00d5dbac2d245284219610582293e9d048949f608a3b4988228b7266`.
Reference host: Ryzen 7 5700U (8 cores / 16 logical CPUs), Linux
7.0.0-38-generic, local ext4. Rerun comparisons on the same host and storage.

The non-Git fixture contains 1,024 Rust files in 16 groups and one Markdown file,
with 746,554 initial source bytes. Each Rust file contains:

```python
"//! Generated indexing reference fixture.\n" + "".join(
    f"pub fn item_{i}_{j}(n: u64) -> u64 {{ n.saturating_add({j}) }}\n"
    for j in range(12)
)
```

File names are `src/group_{i//64}/module_{i}.rs`. The Markdown source links to
`src/group_0/module_0.rs`. Run `init`, `scan`, `symbols build`, and two
`watch --once` no-ops, then append one distinct exported function to module 0
and measure another `watch --once`. Repeat three times; subsequent first steps
are scans. Two additional initial samples use fresh unindexed copies of the
final source fixture (including the three tiny added functions). Record elapsed
time around the entire process and GNU time peak RSS; retain JSON reports to
confirm parsed/indexed counts. This reference supplies targets, not broad parser
or high-degree-graph coverage.

The three rounds yield one initial sample and five full scans: one explicit
scan per round plus two replacement first steps. The fresh copies add the
remaining two initial samples.

## Targets and architecture decision

- Initial/full/rebuild each improve median latency and corresponding throughput
  by at least 10% on this reference, with complete required parsing/projection
  work. Maximum RSS may not exceed its baseline by more than 10%.
- Cold sparse refresh improves median latency by at least 50%, parses only
  changed source and genuinely affected dependencies, and preserves complete
  results and authored state. Dense changes and wider invalidation retain exact
  fallback under the existing resource limits.
- Cold unchanged refresh stays below 60 ms median on this reference and has no
  new publication or parse work. It uses one exact discovery and an ordered
  source-only database comparison. A fresh process has no trustworthy offline
  event history; it must inspect source bytes, including same-metadata edits.
  The measured discovery cost is acceptable, so no retained-history service is
  proposed.
- An unchanged MCP refresh uses one exact source detection/comparison, with no
  full-node decode, parsing or publication and no median latency regression beyond
  10% of its paired native baseline. Warm MCP does not claim an RSS measurement. The accepted RC1 scope
  defers zero-source-work warm admission to unscheduled #725.
- Final acceptance must register named unaffected-navigation and supported-upgrade
  baselines before comparing them; their median latency and peak RSS may each
  increase by at most 10%. Those cases are not measured by this reference.
  Failure, cancellation, source races, writer races, and rollback
  retain identity, approved purposes, and the last complete publication.

Use the existing concrete refresh and RAII publication owners. Compare ordered
source fields without joining or decoding purpose/summary state. Feed discovered
changes through the existing dependency-aware incremental owner. Capture and
reuse source evidence within one operation; retain exact publication validation
until an equivalent source/writer witness is proven. No schema, new pool, tuning
pragma, daemon, or independent indexing framework is justified by this reference.

For explicit MCP refresh, reuse operation-owned exact source comparison and
transfer changed evidence to the existing mutable owner without a second detection
scan. Retained read epochs and empty notification queues cannot prove current
source state. Full/policy uncertainty returns to exact work under the same clock.
The existing normal-read repair cap remains independent of explicit refresh.

Keep work-count checks independent of time measurements. The complete release
matrix must additionally cover larger file/byte counts, dense graphs, supported
parser/document cases, warm MCP, arbitrary mixed changes, lost/offline events,
policy invalidation, plain directories, concurrency, upgrade and rollback on
Linux x64, Windows x64, macOS Intel and Apple Silicon. These boundaries have not
yet passed; this document makes no optimized-result claim.

The full-build change reuses the existing storage-owned bulk-index policy:

in paired full-scan runs. It was removed rather than retained as an unproven

#### Automatic budget coefficients

The Linux reference above completes full work in 3–7 seconds. Defaults deliberately
allow generous cooperative headroom; they do not define performance acceptance.
Only already-required source inventories and verification counters supply estimates.
Before that evidence is available the operation has the existing 1,800-second ceiling;
a cold initial publication with no baseline retains it. No estimator walks the tree.

For an existing full scan/rebuild or admitted incremental publication, select seconds:

`min(1800, 30 + ceil(admitted_entries / 32) + ceil(admitted_bytes / 4096) + 2 * (ceil(verification_entries / 4096) + ceil(verification_bytes / 67108864)))`.

Verification is the complete current inventory because final publication safety still
requires exact validation. The factor two reserves headroom for discovery already
consumed and final verification. Admitted work includes affected source; existing
bounded graph-closure processing shares the same budget. These coefficients include
at least 30 seconds for graph/purpose/parser/publication work even for a tiny delta.
Unknown sizes or overflowing estimates retain 1,800 seconds. Incremental deletion
retains that ceiling because the surviving source inventory does not size the old
projection removal. Full replacement selects a smaller budget only when its
already-required reusable-hash cursor also supplies complete prior entry/byte
work and neither total shrinks. Full work without that prior witness retains the
ceiling; the estimator adds no persisted-source pass. Symbol-only rebuild already
consumes the existing work inventory. Dense dependency-closure headroom still
requires the registered representative measurements before acceptance.

For an unchanged refresh use `min(1800, 5 + ceil(discovered_entries / 4096) +
ceil(discovered_bytes / 67108864))`; source discovery remains required for explicit one-shot refresh. Check the selected deadline before returning.

Every selection is a ceiling derived from the operation's original start, preserving
earlier caller deadlines, cancellation and resource accounting. Explicit timeouts,
including an explicit 1,800 seconds, bypass automatic selection; larger representable
requests clamp at 1,800, zero refuses, and unrepresentable deadlines fail closed.
Wider fallback selects its full-work default from the original operation boundary,
never a fresh clock; cancellation or deadline failure is not fallback permission.

## Unaffected-navigation and compatible-open comparison protocol

Register these cases before measuring the completed candidate. Use the same
1,024-file reference above and normal telemetry, published 0.5.0 and the optimized
candidate on the same host/filesystem. Record each exact binary digest and version.
Use nine alternating fresh-process samples per runtime after one discarded warm-up;
keep filesystem caches warm and measure the complete process and peak RSS.

- File summary: `--format json summary src/group_0/module_0.rs --limit 10`.
  Verify the selected path and useful source facts, not merely successful exit.
- Detailed relation page: `--format json symbols relations --view detailed --file
  src/group_0/module_0.rs --symbol item_0_0 --limit 10 --output-bytes 32768`.
  Verify the selected declaration and its one call relationship, coverage and totals;
  do not substitute an empty file page or legacy output.
- Compatible current-contract open: `--format json watch --once` against each
  runtime's isolated fixture initialized under its own current semantic contract.
  Check project identity, approved purpose, generation and source/graph counts
  remain unchanged after every sample. This is steady-state source reconciliation,
  not a first open of an older semantic projection. The separate semantic-contract
  upgrade protocol below restores a prior 0.5.0 database and measures required
  repair against complete baseline work; predecessor rollback follows its timings.
  Older predecessor schema migrations retain the existing installed contracts.

Each candidate median latency and maximum RSS must remain within 110% of its
corresponding baseline. Save raw samples and any refusal or mismatch; a failed
case is not an omitted sample. Paired comparisons on the other three release
platforms use their own predecessor native archive and candidate package, rather
than comparing their absolute timings with Linux. No measurements or acceptance
are claimed by registering this protocol.

### Expanded refresh comparison targets

The first draft run was a candidate-only harness/correctness probe on the expanded
fixtures; its numbers are not acceptance evidence. Before the first paired expanded
comparison, register three alternating baseline/candidate sparse samples per fixture.
Large-file/byte sparse refresh must reduce median latency by at least 50%; dense
refresh must reduce it by at least 10%, with maximum sampled RSS at most 110% of its
own same-host baseline. Both must parse exactly the changed file and publish its
added declaration once; the large candidate must also stage exactly one text.
The dense closure can require full graph fallback under existing row limits while
still reusing unchanged parser results. Keep raw work reports and complete-scan
convergence checks so full reparsing cannot masquerade as an affected update.
These expanded targets are selected from the existing sparse/full improvement
policies before viewing a paired result, not fitted to the draft probe's timings.

Run the candidate-only zero-budget/failure/retry proof after the paired timing
rounds, so it cannot warm only the candidate before a measured sparse sample.

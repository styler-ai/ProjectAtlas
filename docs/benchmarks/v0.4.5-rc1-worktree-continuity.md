# v0.4.5-rc1 worktree continuity measurement

This focused release-candidate measurement covers the worktree registry, baseline hydration, target reconciliation, alias routing, repository token aggregation, and high-registration SQLite path. The measured `0.4.5-rc1` runtime was built from the current working tree based on head `7f8ce515312bdddf359287ea1f34454fc369354a`; its exact identity and SHA-256 are recorded in the [raw result](v0.4.5-rc1-worktree-continuity.json).

The deterministic fixture contains 1,024 Rust callers plus their module root and support files. The control checkout is fully indexed before a linked worktree changes one caller, changes the high-fan-out module root, and adds one source file. The real MCP sequence lists the linked candidate, assigns a stable alias, initializes that alias from the control database, queries its overview, and requests repository-wide token totals from `main`. ProjectAtlas does not create, move, or remove the Git worktree.

## Result

| Metric | Control full scan | MCP worktree sequence |
| --- | ---: | ---: |
| Wall time | 1.879472 s | 4.700160 s |
| Process-tree CPU time | 2.218750 s | 5.015625 s |
| Peak process-tree RSS | 37,892,096 B | 49,942,528 B |
| Process read transfer | 102,192,816 B | 492,966,345 B |
| Process write transfer | 449,001,424 B | 927,030,288 B |
| Persistent target growth | n/a | 18,284,544 B |
| Maximum single MCP response | n/a | 6,908 B |
| Final control / target WAL | n/a | 0 B / 0 B |

Hydration copied the complete control publication at generation 1 and published the reconciled target at generation 2. Exact source verification found the three changed paths. Symbol parsing processed only those three files and retained 1,025 unchanged files; structural summaries likewise processed three files. The changed module root intentionally exercises the dependency-closure ceiling, so the graph layer safely falls back to its complete publication path. The resulting `50.700214x` process-write-transfer-to-persistent-growth ratio is reported as measured write amplification, not hidden or presented as a speedup.

The timeout-zero `BEGIN IMMEDIATE` samplers made 198 control-database attempts and 12 target-database attempts. Neither database observed a busy sample; the conservative maximum sampled upper bounds were 0.050424 seconds for control and 0.040596 seconds for target.

The high-registration probe inserted 128 worktree registrations and one sealed routed event per registration. Its exact owning database test traced 11,151 SQLite statements and 3,203 changed rows, used the owning registry and aggregate indexes, completed in 3.122656 seconds with 0.953125 CPU seconds and 25,092,096 B peak RSS, and left no active MCP telemetry instances. All harness gates passed, including exact three-file parsing, alias telemetry aggregation, bounded output/WAL, query-plan ownership, target isolation, and unchanged Git lifecycle.

These are single-host Windows measurements. They are not cross-platform latency claims, a provider-token benchmark, or proof that every worktree change is incremental: high-fan-out changes may deliberately require a complete graph publication while still reusing unchanged source parsing and the hydrated database.

## Reproduction

Build the release-profile candidate, then run:

```powershell
python -B docs/benchmarks/harness/worktree_continuity.py --runtime target/release/projectatlas.exe
```

On Unix, pass `target/release/projectatlas`. The harness also runs the exact owning SQLite probes:

```text
cargo test --locked -p projectatlas-db telemetry::tests::worktree_continuity_high_registration_aggregate_has_bounded_sql_and_rows -- --exact --nocapture
cargo test --locked -p projectatlas-db worktree_registry::tests::hot_registry_and_aggregate_lookups_use_owning_indexes -- --exact --nocapture
```

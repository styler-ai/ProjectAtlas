# ProjectAtlas v0.4 Agent Navigation Evaluation

> **Interim task 5.8 checkpoint — not the release benchmark.** These results
> describe the compatibility-preserving task-5.8 candidate on 2026-07-23.
> OpenSpec task 7.6 requires a fresh, repeated, publication-quality three-way
> benchmark after tasks 7.1 through 7.5 and the exact release candidate stabilize.

## Outcome

All three arms reached the correct source evidence on clean, dirty-worktree, and
non-Git fixtures. Relative to frozen ProjectAtlas v0.3.26, the v0.4 candidate
used 43.8% fewer ProjectAtlas calls, eliminated the three recorded backtracks,
and emitted 12.3% fewer task-evidence bytes.

Compatibility has a measurable cost. The complete v0.4 MCP discovery payload is
37,011 bytes per session, 27.9% larger than v0.3.26's 28,933 bytes. Runtime
navigation bytes therefore increased 20.4% despite the shorter evidence routes.
The packaged v0.4 skill is 13,666 bytes, 59.8% smaller than the frozen 33,977-byte
v0.3.26 skill. Including the matching skill once in each independent cold
session makes v0.4 18.8% smaller overall than v0.3.26.

The no-ProjectAtlas control remains far smaller on these deliberately tiny
5-to-19-line fixtures. Neither ProjectAtlas version breaks even here. The
ProjectAtlas arms avoid broad filesystem source reads and return bounded indexed
context plus exact slices; whether that fixed cost repays itself on medium and
large repositories belongs to task 7.6.

boundary; it is not a fresh stochastic model comparison. Baseline agent timing
and current transport-runner timing are not treated as comparable. Task 7.6 must

## Runtime Navigation Results

`Evidence bytes` are UTF-8 MCP response or shell-result bytes used after tool
discovery. `Discovery bytes` are the ProjectAtlas-specific `tools/list` array;
the common shell surface has no incremental ProjectAtlas discovery cost.
`Runtime bytes` are evidence plus discovery. `Context estimate` is
`ceil(runtime bytes / 4)`, a reproducible heuristic rather than provider billing
tokens.

Relative to v0.3.26, the compatibility-preserving candidate:

- reduced calls from 32 to 18: **43.8%**;
- reduced backtracks from 3 to 0: **100%**;
- reduced task-evidence bytes from 19,913 to 17,461: **12.3%**;
- increased discovery bytes per session from 28,933 to 37,011: **27.9%**; and

The discovery regression is reported as a regression. Preserving all v0.3.26
tool names, descriptions, request schemas, defaults, and compatible payload

discovery-size claim. Public inventory rationalization belongs to issue #310.

## Compatibility Boundary

The candidate preserves the complete frozen v0.3.26 surface:

- all 40 tool names and descriptions;
- complete recursive request-schema trees;
- omitted-argument defaults, including session-brief limit 5;
- legacy file-summary payload behavior;
- warning and error blockers; and
- shared service serialization.

The frozen surface is checked against
`crates/projectatlas-cli/tests/fixtures/mcp-v0.3.26-tools.json`. V0.4 compact
navigation is additive and explicit through `compact: true` on
`atlas_session_brief` and `atlas_file_summary`. Compact projection stays in the
MCP adapter and reuses the already bounded legacy report; it adds no database
query, worker, lock, crate, whole-graph materialization, or unbounded collection.

## Broad And Full-File Read Behavior

The ProjectAtlas arms performed no broad filesystem source read. They used
indexed metadata and exact slices. Some slices span an entire tiny fixture file;
those are intentional exact evidence, not broad repository escapes.

The no-ProjectAtlas arm used 14 broad listings/searches and displayed 11
effectively complete tiny source files across the three tasks. This is not
treated as a failure: on tiny inputs, direct reads are the cheaper tool. The
final benchmark must identify where bounded indexed navigation actually crosses
that fixed-cost boundary.

## Limits And Final Rerun Gate

This checkpoint proves compatibility-preserving routing and exact evidence on
three tiny fixtures. It does not provide stochastic distributions or comparable
agent timing and does not measure indexing, startup, persistent bytes, CPU, peak
RSS, warm-cache behavior, or medium/large break-even.

Task 7.6 supersedes this report for release publication. After tasks 7.1 through
7.5 stabilize the exact candidate, the final benchmark must:

1. rerun all three arms from scratch with identical model, reasoning, permissions,
   prompts, fixtures, cache policy, and instrumentation;
2. cover clean, dirty, non-Git, small, medium, and pinned real-source large/huge
   work;
3. repeat stochastic trials and publish distributions plus every failed or
   excluded run;
4. measure correctness, calls, reads, backtracking, emitted and total context,
   elapsed time, CPU, peak RSS, indexing/startup/storage cost, and break-even;
5. publish raw machine-readable results, prompts, environment/candidate
   identities, rerun commands, limitations, and candidate provenance; and
6. make only the reviewed final result—not this interim checkpoint—prominent
   from the repository landing page.

# ProjectAtlas v0.4 Agent Navigation Evaluation

> **Final task-7.6 publication benchmark.** All 45 preregistered trials are
> retained. Three frozen-v0.3.26 huge-corpus trials failed during setup; no run
> was excluded or replaced.

## Headline

ProjectAtlas v0.4 completed all 15 assigned source-navigation trials. Frozen
ProjectAtlas v0.3.26 completed 12 of 15 and failed all three pinned VS Code
setups on a tracked non-UTF-8 source file. The no-ProjectAtlas control completed
all 15.

Manual review accepted the source claims and substantive answer in all 42
completed trials. One otherwise-correct v0.4 answer used invalid temporary-root
citation targets, so the final manual result is **41/42 completed answers**,
including **14/15 for v0.4**, **12/12 for frozen v0.3.26**, and **15/15 for the
plain control**.

The efficiency result is mixed and does not support a universal saved-token
claim:

- Against frozen v0.3.26 on the three small tasks, v0.4 reduced median total
  tool calls by 23.1% to 38.9% and net navigation context by 28.1% to 29.6%.
- On the medium 1,024-caller task, v0.4 tied the frozen baseline's median 18
  calls and used 66.7% fewer median full reads, but used 47.3% more net
  navigation context and took 51.5% longer including setup.
- No honest huge-corpus comparison with v0.3.26 exists because every frozen
  setup failed. Against the plain huge-corpus control, v0.4 eliminated median
  broad reads but used 502.3% more net navigation context and paid a median
  618.1-second, 2,362.6-MiB peak-RSS, 3,809.7-MiB persistent-index setup.
- The plain control used the least navigation context at every scale in this
  campaign. ProjectAtlas's demonstrated value is structured source selection,
  fewer broad/full reads in several cases, exact current-source evidence, and
  compatible indexed navigation—not automatic context or latency superiority
  for every repository question.

Three repeats support the reported values, median, and observed maximum only.
The observed maximum is the preregistered tail statistic; it is not a stable
p95 estimate.

## Reconciliation With Task 7.4

The publication-eligible task-7.4 system matrix independently measured the
functional v0.4 storage/query design before the final candidate-only UTF-8
header fix:

| Scale | Corpus | Full scan | Peak process RSS | Persistent database | Result |
| --- | --- | ---: | ---: | ---: | --- |
| Small | 6–7 files; clean, dirty, and non-Git | 0.16–0.30 s | 10.4–12.9 MiB | 0.47–0.53 MiB | all checks passed |
| Medium | 1,028 files | 1.71 s | 35.3 MiB | 16.45 MiB | all checks passed |
| Huge | pinned VS Code, 16,646 tracked files and 235,792,515 bytes | 609.05 s | 2,359.5 MiB | 3,809.5 MiB | all checks passed |

The exact final candidate then passed a release-runtime VS Code smoke in
614.77 seconds with 2,476,515,328 bytes peak RSS and a 3,994,755,072-byte
database, correctly classifying 213 non-UTF-8/binary text inputs and 14
structural inputs, with no final WAL, SHM, or staging state. The final
navigation campaign's median 618.1-second setup, 2,362.6-MiB peak RSS, and
3,809.7-MiB persistent index are consistent with that matrix.

This agreement supports the resource accounting; it does not turn the large
setup cost into a benefit. V0.4's bounded huge-corpus queries and cleanup
passed, while full indexing remains an expensive trade-off that should be
amortized only across sustained repository work.

## Token-Overview Reconciliation

The controlled three-arm benchmark measures exact task navigation output and
charges each arm for its own packaged skill, tool discovery, and setup context.
It therefore supplies the direct counterfactual used in this report.

`atlas_token_report` has a different contract:

- observed summary/slice replacements are measured against the file bytes they
  replace;
- search narrowing estimates likely avoided file reads from bounded candidate
  selection;
- modeled navigation avoidance remains labeled as modeled or inferred;
- repeated modeled baselines are deduplicated for the conservative
  `tokens_avoided` headline; and
- provider counters remain a separately labeled observation.

Those categories are not interchangeable. The token-overview UI must not use
its modeled aggregate to contradict this campaign's plain-control result, and
this report must not use provider billing counters as proof that ProjectAtlas
caused a token difference.

## Limitations And Decision

- Three repeats expose stochastic values, a median, and an observed maximum;
  they do not establish a stable percentile distribution.
- Provider cache state is not independently controlled. Provider counters are
  descriptive, not causal navigation evidence.
- Frozen v0.3.26 produced no huge-corpus answer, so no v0.4-versus-v0.3.26
  correctness, context, latency, or resource percentage is claimed there.
- The deterministic exact-term rubric has both false negatives and one
  citation-quality false positive; manual review is the final answer-quality
  boundary.
- Temporary trial roots were removed. Durable verification uses the checked-in
  fixtures, medium generator, and pinned VS Code commit rather than expecting
  redacted answer links to remain clickable.
- The tasks exercise source navigation, not implementation quality, issue
  completion, or arbitrary repository work. Results do not generalize to every
  model, host, repository, or prompt.
- Plain source navigation won total context on every measured corpus. V0.4's
  accepted result is therefore compatibility, complete execution, correct
  current-source navigation, and several call/read improvements with explicitly
  reported medium-context and huge-setup costs—not a universal efficiency win.

The benchmark satisfies task 7.6's publication and non-cherry-picking contract.
It preserves the stronger earlier task-7.3 compatible-workflow result while
making the broader final trade-offs visible.

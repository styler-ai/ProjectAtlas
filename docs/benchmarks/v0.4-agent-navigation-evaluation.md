# ProjectAtlas v0.4 Agent Navigation Evaluation

> **Final task-7.6 publication benchmark.** All 45 preregistered trials are
> retained. Three frozen-v0.3.26 huge-corpus trials failed during setup; no run
> was excluded or replaced.

## Headline

ProjectAtlas v0.4 completed all 15 assigned source-navigation trials. Frozen
ProjectAtlas v0.3.26 completed 12 of 15 and failed all three pinned VS Code
setups on a tracked non-UTF-8 source file. The no-ProjectAtlas control completed
all 15.

Manual review accepted the source claims and substantive answer in all 42
completed trials. Seven otherwise-correct answers used invalid temporary-root
citation targets, so the final manual result is **35/42 completed answers**:
**12/15 for v0.4**, **11/12 for frozen v0.3.26**, and **12/15 for the plain
control**.

The efficiency result is mixed and does not support a universal saved-token
claim:

- Against frozen v0.3.26 on the three small tasks, v0.4 reduced median total
  tool calls by 23.1% to 33.3% and net navigation context by 18.5% to 19.6%.
- On the medium 1,024-caller task, v0.4 used 11.1% more median calls and
  2,356.8% more median net navigation context, and took 21.9% longer including
  setup. It used 40% fewer median productive files and eliminated median broad
  reads and backtracks.
- No honest huge-corpus comparison with v0.3.26 exists because every frozen
  setup failed. Against the plain huge-corpus control, v0.4 used 386.8% more
  median net navigation context and paid a 763.1-second, 2,361.4-MiB peak-RSS,
  3,809.6-MiB persistent-index setup.
- The plain control used the least navigation context at every scale in this
  campaign. ProjectAtlas demonstrated structured source selection, fewer
  broad/full reads in several cases, exact current-source evidence, and
  compatible indexed navigation—not automatic context or latency superiority.

Three repeats support the reported median and observed maximum only. The
observed maximum is the preregistered tail statistic; it is not a stable p95.

## Token-Overview Reconciliation

The controlled three-arm benchmark measures exact task navigation output and
charges each arm for its own packaged skill, tool discovery, and setup context.
`atlas_token_report` has a different contract:

- observed summary/slice replacements are measured against file bytes;
- search narrowing estimates likely avoided file reads;
- modeled navigation avoidance remains labeled modeled or inferred;
- repeated modeled baselines are deduplicated for the conservative headline;
- provider counters remain separately labeled observations.

Those categories are not interchangeable. Neither the token UI nor this report
may relabel modeled or provider counters as a universal causal saving.

## Limitations And Decision

- Three repeats expose a median and observed maximum, not a stable percentile.
- Provider cache state is not independently controlled; counters are descriptive.
- Frozen v0.3.26 produced no huge answer, so no huge v0.4-versus-v0.3.26
  correctness, context, latency, or resource percentage is claimed.
- Exact-term matching has false negatives, and citation quality needs independent
  review; manual review is the final answer-quality boundary.
- Trial roots were removed. Durable verification uses checked-in fixtures, the
  medium generator, and the pinned VS Code commit.
- These tasks exercise source navigation, not arbitrary repository work.
- Plain navigation won total context on every corpus. V0.4 is accepted for
  compatible, correct current-source navigation and several call/read
  improvements with explicit medium-context and huge-setup costs—not a universal
  efficiency win.

The campaign satisfies task 7.6 publication and non-cherry-picking requirements
against the corrected functional release candidate.

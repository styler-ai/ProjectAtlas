# ProjectAtlas v0.4 Agent Navigation Evaluation

> **Historical task-7.6 publication benchmark.** All 45 preregistered trials are
> retained, but candidate-owned inputs changed afterward, so these measurements
> are historical rather than current v0.4 release proof. Three frozen-v0.3.26
> huge-corpus trials failed during setup; no run was excluded or replaced.

## Decision

ProjectAtlas v0.4 completed all 15 assigned source-navigation trials. Frozen
ProjectAtlas v0.3.26 completed 12 of 15 and failed all three pinned VS Code
setups on a tracked non-UTF-8 source file. The no-ProjectAtlas control completed
all 15.

Manual review accepted the source claims and substantive answer in all 42
completed trials. Twelve otherwise-correct answers used malformed temporary-root
citation targets, so the final citation-valid result is **30/42 completed
answers**: **12/15 for v0.4**, **9/12 for frozen v0.3.26**, and **9/15 for the
plain control**.

The efficiency result is mixed:

- V0.4 used less median navigation context than v0.3.26 on all three small
  tasks and fewer median tool calls on each.
- V0.4 used substantially more navigation context on the medium task and paid
  a large one-time setup cost on the pinned VS Code corpus.
- The plain control used the least navigation context on every corpus.
- ProjectAtlas demonstrated compatible indexed navigation, current-source
  selection, and fewer broad/full reads in several cases. This campaign does
  not support a universal token-saving, latency, or cost claim.

Three repeats support the reported median and observed maximum only. The
observed maximum is the preregistered tail statistic; it is not a stable p95.

V0.4's median huge-corpus setup alone took 731.33 seconds, peaked at about
2,363 MiB RSS, and left about 3,809.6 MiB of persistent index state. No honest
huge v0.4-versus-v0.3.26 percentage exists because every frozen setup failed.
Full huge-source indexing should be amortized only across sustained repository
work.

All three medium v0.4 rows used 16 tool calls, 15 of them ProjectAtlas MCP
calls. Net navigation output ranged from 100,750 to 488,681 bytes, with a
442,519-byte median. Median setup was 2.27 seconds and median cold wall time was
253.39 seconds; one row still reached 571.45 seconds cold, so the campaign
continues to show latency variance. This evaluation does not infer a
broad-read-reduction claim from agent self-audits.

Provider-owned token counters remain descriptive only. Provider cache state was
not independently controlled, so the machine artifact reports those counters
separately and does not attribute their differences causally to navigation.

## Task-7.4 System Reconciliation

The historical system-scale campaign used the same functional v0.4 candidate as
the navigation campaign at the time. All 335 ordinary checks passed across
clean, saved-dirty, non-Git, medium high-degree, and pinned VS Code cases.
Concurrent isolation, publication contention/retry, cooperative
cancellation/reopen, and forced parent termination/recovery also passed. Its
measurements are retained for comparison but are not publication-eligible for
the current source because candidate-owned inputs changed afterward.

For that historical candidate, the campaign recorded passing
scan/query/incremental, bounded-resource, recovery, and platform behavior. It
neither establishes current-source readiness nor turns the observed large setup
cost into a benefit.

## Token-Overview Reconciliation

This controlled three-arm benchmark measures task navigation output and charges
each ProjectAtlas arm for its own packaged skill, tool discovery, and setup
context. `atlas_token_report` has a different contract:

- observed summary and slice replacements are measured against file bytes;
- search narrowing estimates likely avoided file reads;
- modeled navigation avoidance remains labeled modeled or inferred;
- repeated modeled baselines are deduplicated for the conservative headline;
- provider counters remain separately labeled observations.

Those categories are not interchangeable. Neither the token UI nor this report
may relabel modeled or provider counters as a universal causal saving.

## Reproduction

The full campaign is manual-only. Standard CI, pre-push, prepublication, merge,
and release paths never execute it; run the command below only after an explicit
user request. Focused harness unit tests and publication-integrity checks remain
normal validation.

```powershell
python docs\benchmarks\harness\agent_navigation.py `
  --preregistration docs\benchmarks\v0.4-agent-navigation-preregistration.json `
  --output target\benchmarks\agent-navigation\agent-navigation-final.json `
  --work-root target\benchmarks\agent-navigation\final `
  --corpus-cache target\benchmarks\system-scale\corpus-cache `
  --repeats 3

$filter = @'
del(.runs[].raw_jsonl)
| (.runs[].trace.mcp_calls[]?.arguments
    | select(has("cursor") and (.cursor | type == "string")))
  |= (. + {cursor_bytes: (.cursor | utf8bytelength)}
      | .cursor = "{OPAQUE_CURSOR_OMITTED}")
'@

jq --indent 2 $filter `
  target\benchmarks\agent-navigation\agent-navigation-final.json `
  > docs\benchmarks\v0.4-agent-navigation-results.json
```

The harness refuses retained output or journals, validates the functional
candidate and preregistration, rotates arm order, records every scheduled row,
verifies source state, redacts local paths, and removes only
ownership-validated work roots. Publication removes redundant provider JSONL
and bounds opaque transport cursors; every scheduled row and reader-visible
field remains.

## Limitations

- Three repeats expose a median and observed maximum, not a stable percentile.
- Provider cache state is not independently controlled; counters are
  descriptive.
- Frozen v0.3.26 produced no huge answer, so no huge
  v0.4-versus-v0.3.26 correctness, context, latency, or resource percentage is
  claimed.
- Exact-term matching has false negatives, and citation quality needs
  independent review; manual review is the final answer-quality boundary.
- Trial roots were removed. Durable verification uses checked-in fixtures, the
  medium generator, and the pinned VS Code source.
- These tasks exercise source navigation, not arbitrary repository work.
- Plain navigation won total context on every corpus.

At the time it ran, the campaign satisfied the task-7.6 publication and
non-cherry-picking requirements against its functional candidate. It is now a
historical record, not current v0.4 release proof. Release-readiness task 4.4
remains open until its remaining validators, live review dispositions, and
release-candidate gates complete.

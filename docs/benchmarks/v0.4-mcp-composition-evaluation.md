# ProjectAtlas v0.4 MCP Composition Evaluation

## Status

This protocol was preregistered before the formal task-7.3.1 run. Earlier
interactive calls used to validate fixture compatibility and choose credible
comparison arms are exploratory and are excluded from the reported result.

## Decision

The evaluation decides whether the compatible v0.4 MCP calls are sufficient
for six graph-navigation questions or whether v0.4 needs one small additive
change. It cannot remove, rename, consolidate, or change the default behavior
of any pre-v0.4 tool. Those broader decisions belong to issue #310.

## Frozen Candidate And Fixtures

- Candidate: the exact `projectatlas 0.4.0` branch build under evaluation.
- Baseline compatibility fixture:
  `crates/projectatlas-cli/tests/fixtures/mcp-v0.3.26-tools.json`.
- Clean Git fixture: `target/agent-workflows/clean`.
- Dirty-worktree fixture: `target/agent-workflows/dirty`.
- Non-Git fixture: `target/agent-workflows/non-git`.
- Telemetry: disabled.
- Cache policy: one new MCP process per fixture and arm; one fixture index is
  built before timing and reused unless the freshness scenario changes source.
- Tool discovery: measured once per arm as compact serialized `tools/list`.

The same task wording, expected files, symbols, relation direction, correctness
rubric, call order, and limits are used across arms. The dirty freshness
scenario edits saved source after its index exists and must either reconcile
the affected closure or return a typed non-stale refusal.

## Questions And Correct Answers

| ID | Question | Clean | Dirty worktree | Non-Git |
| --- | --- | --- | --- | --- |
| Q1 | Where is this behavior implemented? | `src/storage.rs::save_order` | `src/pricing.rs::apply_discount` | `src/config.rs::load_timeout_millis` |
| Q2 | Which callers are affected if this symbol changes? | `src/api.rs::submit_order` | `src/pricing.rs::calculate_total`, then `src/checkout.rs::checkout_total` | `src/handler.rs::health_response`, then `src/router.rs::dispatch` |
| Q3 | Why is this file relevant? | order-write purpose plus caller connection | pricing-policy purpose plus checkout connection | configuration-reader purpose plus handler connection |
| Q4 | Which relation is resolved, ambiguous, external, or unresolved? | typed status and trust from the relation response | same | same |
| Q5 | Did this edit invalidate dependent graph state? | current generation or typed refusal | post-index saved threshold edit and affected caller refresh | current generation or typed refusal without Git |
| Q6 | Show the smallest trustworthy source slice after following the relationship. | exact caller symbol slice | exact caller symbol slice | exact caller symbol slice |

Q4 is correct only when the response distinguishes all supported resolution
states and does not turn incomplete coverage into a negative claim. A fixture
does not need to manufacture every status when the same selected response
schema and owning tests cover the missing states.

## Arms

### A. Compatible Current Routes

Use only the frozen calls and current payloads:

```text
atlas_session_brief
→ atlas_file_summary
→ atlas_symbol_relations(view = detailed or analysis)
→ atlas_slice
```

Only calls needed by a question count. A response forced below the size needed
to retain one correct row is a bounded failure, not a correct answer.

### B. Smallest Additive Existing-Route Change

Add an opt-in compact projection to `atlas_symbol_relations`. It must use the
same relation service and retain:

- exact anchor and reusable target selectors;
- relation kind, direction, resolution, confidence, and completeness;
- generation, purpose revision, purpose state, and coverage/trust;
- occurrences when requested, path selectors for multi-hop results, and
  existing next-call guidance;
- totals, truncation, continuation, reached limits, and bounded work.

The legacy and non-compact request and response remain byte-for-byte compatible
for the same existing inputs.

### C. Dedicated Graph-Question Tool

The smallest credible new tool would accept a task query, optional exact anchor,
closed question mode, and existing relation limits, then route to the same brief,
relation, and slice services. Its schema bytes, required calls, and output are
counted even though the design is rejected without implementation when it
cannot beat arm B without becoming an orchestration catch-all.

## Measurements

For every question and fixture, record:

- answer correctness and reusable-selector correctness;
- freshness generation or typed refusal, purpose state, coverage, confidence,
  completeness, and resolution evidence;
- required calls and backtracking;
- emitted response bytes, relevant tool-schema bytes, full discovery bytes,
  and cold-session total bytes;
- per-call and route elapsed time;
- correct bounded behavior under a deliberately too-small output budget.

Machine-readable results must identify the exact candidate, fixture, request,
response byte count, elapsed time, and rubric disposition. Failed and excluded
runs remain visible.

## Selection Rule

Keep arm A when it is best or tied. Select arm B only when it preserves every
correctness, trust, selector, freshness, compatibility, and bounded-failure
result while reducing median detailed-relation bytes by at least 40% and
question-route bytes by at least 20%, with no extra call and no material latency
regression. Select arm C only if it then removes at least one median call and a
further 20% of route bytes without hiding trust or becoming a generic router.

After selection, rerun the complete 0.3.26 MCP compatibility E2E and refresh
the packaged v0.4 discovery measurement. No result from this evaluation permits
removing useful calls such as summary, search, relation navigation, or slice.

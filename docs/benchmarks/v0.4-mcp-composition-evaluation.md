# ProjectAtlas v0.4 MCP Composition Evaluation

## Outcome

The compatible ProjectAtlas v0.4 MCP surface is sufficient for the six
canonical graph-navigation questions. The selected design keeps all 40
pre-v0.4 tools and adds compact opt-in payload behavior to existing calls. No
new graph-question tool is justified for v0.4.

The deterministic six-question harness passed every answer, selector, trust,
freshness, and bounded-failure rubric on clean Git, saved-dirty Git, and
non-Git fixtures. Compact relation routes reduced emitted bytes by 55.9–57.5%,
median relation bytes by 50.0–63.4%, and median question bytes by 55.6–61.9%
without adding a call.

The blind task-7.3 agent comparison also passed every fixture. Against frozen
v0.3.26, v0.4:

- reduced calls from 34 to 24 (29.4%);
- reduced recorded backtracks from two to zero;
- avoided all three broad `atlas_files(include_content: true)` reads;
- reduced emitted MCP evidence bytes from 19,094 to 15,295 (19.9%);
- reduced emitted evidence bytes on every fixture, including 6.3% on non-Git;
- increased discovery-plus-response bytes from 105,893 to 127,192 (20.1%)
  because the complete compatible discovery schema is larger; and
- reduced cold context including the matching packaged skill from 207,824 to
  174,772 bytes (15.9%).

The discovery-only regression is not hidden. Both versions advertise 40 tools;
v0.4 discovery is 37,299 bytes versus 28,933 for v0.3.26. Public
classification, compact/default inventory selection, alias consolidation, and
breaking removal remain conscious post-v0.4 work in issue #310.

This report closes the OpenSpec 7.3/7.3.1 decision boundary. It is not the
publication-quality release benchmark: task 7.6 must repeat the final
v0.4/v0.3.26/no-ProjectAtlas comparison across small, medium, and pinned
real-source large/huge work.

## Preregistered Decision

The evaluation asks whether the compatible v0.4 routes can answer:

1. Where is this behavior implemented?
2. Which callers are affected if this symbol changes?
3. Why is this file relevant?
4. Which relation is resolved, ambiguous, external, or unresolved?
5. Did this saved edit invalidate dependent graph state?
6. What is the smallest trustworthy source slice after following the
   relationship?

The compared designs were:

- **Arm A:** existing compatible routes and full payloads.
- **Arm B:** the smallest additive opt-in compact behavior on existing calls.
- **Arm C:** a proposed dedicated `atlas_relation_slice` tool.

Arm B could win only if every correctness, selector, trust, freshness,
compatibility, and bounded-failure result stayed correct while median detailed
relation bytes fell at least 40% and median question-route bytes fell at least
20%, with no extra call or material latency regression. Arm C could win only if
it removed at least one call from every applicable multi-call question and a
further 20% of those route bytes without becoming a generic orchestration
router.

All 36 question/arm/fixture rubrics pass. The timing change is retained as a
single deterministic harness sanity replay, not presented as a latency

The selected compatible improvements are:

- `compact: true` on detailed `atlas_symbol_relations`;
- a typed top-level `next_call` when a truncated relation page can continue;
- empty optional symbol parent/kind/signature values normalized as absent;
- compact file summaries that omit empty legacy symbol documentation, parent,
  and caller sections;
- compact session briefs that retain the reviewed purpose, one crisp
  connection, truncation state, and exact next call without repeating aggregate
  reason/count metadata;
- compact blocker totals with the existing exact `atlas_health` follow-up
  instead of duplicating full finding rows; and
- packaged-skill routing that uses a trusted direct summary connection before a
  detailed relation call, while requiring exact module/export proof for public
  exposure.

Full/default compatibility payloads are unchanged by these compact projections.
No new database query, worker, lock, crate, dependency, unbounded collection,
or whole-graph materialization was added.

## Freshness And Bounded Failure

The dirty saved-edit scenario runs inside one long-lived MCP process. After the
indexed threshold is changed, the next relation read advances generation 1 to
2, keeps the affected caller relation resolved, and the exact slice contains
the current edit. The post-edit relation response is 8,835 bytes and the source
slice is 295 bytes.

Bounded output fails honestly:

| Arm | Limit | Result |
| --- | ---: | --- |
| Full | 4,096 bytes | 3,231-byte truncated envelope, zero rows, reusable continuation |
| Compact | 4,096 bytes | 3,806 bytes, one complete correct row |
| Compact | 2,048 bytes | 118-byte typed error because even the empty envelope cannot fit |

No partial relation row is presented as success.

## Dedicated Tool Decision

The smallest credible Arm C schema is 750 bytes. It could combine the Q6
relation and source calls, lowering the median applicable call count from 1.5
to 1.0. The existing compact relation response alone is already 3,806 of 4,095
clean bytes, 3,698 of 4,022 dirty bytes, and 3,642 of 3,880 non-Git bytes.
Even granting an impossible zero-byte exact-source payload, the maximum
possible reduction is only 7.1%, 8.1%, and 6.1%, respectively; real source
bytes make the achievable reduction smaller. It also adds discovery schema.

Arm C is rejected. A dedicated graph-question tool would duplicate relation and
slice responsibilities without meeting the preregistered byte rule. Useful
summary, search, relation, and slice calls are retained.

## Complete-Support Revalidation

All 23 runtime candidate language profiles were revalidated against the final
MCP navigation contract. Zero were promoted. Every candidate remains at its
strongest independently proved lower tier because none has every required
capability axis plus the complete schema-bound representative-repository and
bounded agent-navigation evidence required for a complete-support claim.

## Exclusions And Limitations

The exclusion manifest records interrupted, cancelled, setup-failed,
unreviewed-purpose, pre-fix, and superseded-candidate runs. None contributes to
the selected tables. In particular, earlier agent trials found real product or
skill defects—empty optional disambiguators, an unusable raw continuation,
unnecessary detailed relation calls, empty legacy summary fields, repeated
briefs, public-boundary misuse, and unreviewed purpose fixtures. Those defects
were fixed, and the complete protocol was rerun instead of cherry-picking a
favorable earlier trace.

This evaluation has two deliberate limits:

- the formal route timings are one deterministic replay per fixture and arm;
- the blind forward test has one stochastic agent trial per arm and fixture.

Task 7.6 must supersede the agent comparison with repeated distributions,
identical three-arm conditions including no ProjectAtlas, system CPU/RSS and
storage/startup/indexing cost, break-even behavior, small/medium/pinned
large/huge work, raw prompts, and every failed or excluded run.

## Why

After v0.5.0 installs a complete short CLI alongside MCP, ProjectAtlas needs one evidence-led public agent surface instead of teaching every transport equally for every task or removing useful MCP capabilities by assumption. The v0.6 boundary must measure the installed v0.5 baseline, preserve successful agent workflows and project isolation, and make the version-matched skill describe the smallest coherent CLI/MCP division.

## What Changes

- Freeze the installed stable v0.5 CLI commands, MCP tool names and schemas, generated host configuration, version-matched skill, discovery bytes, and representative agent-task outcomes as the compatibility baseline.
- Compare CLI-first, MCP-first, and mixed routes on identical startup, orientation, search, exact retrieval, graph, health, purpose, token, administration, routing, freshness, and recovery tasks.
- Retain `atlas ...` as the preferred ordinary one-shot shell route established by v0.5 and retain MCP where no-shell hosts, typed discovery, persistent multi-client routing, session-local background tasks, or another proven capability materially improves the boundary.
- Give every MCP tool and skill route one reviewed disposition: retained, merged into an existing typed response, CLI-owned, automatic backend behavior, or intentionally removed.
- Keep retained schemas concrete and bounded; retain task status/cancellation only when a real packaged operation produces and cancels a task.
- Update runtime, canonical CLI, MCP inventory, plugin skill, generated host expectations, compatibility fixtures, documentation, migration notes, and installed-product proof atomically.
- Treat removals or incompatible schema changes as **BREAKING** and deliver them only through the documented v0.6 compatibility boundary with rollback guidance.

Non-goals:

- No predetermined MCP tool-count target, CLI-only doctrine, MCP-only doctrine, catch-all administration multiplexer, or removal justified only by another product's benchmark.
- No removal of the canonical `projectatlas` command, the concise `atlas` command, explicit project-root isolation, typed errors, freshness guarantees, exact selectors, purpose correction, or safe administrative behavior.
- No Memory Atlas implementation in this change; #314 consumes the stabilized surface afterward.
- No SQLite schema, authored/derived-state, or freshness-model change merely to reclassify or merge adapters; an unavoidable compatibility delta requires a database implication review before dependent work.
- No TUI, browser GUI, or graph visualization work.

This change is ready for implementation after its diagrams, task mirror, issue mapping, and IssueOps planning gate are complete.

## Capabilities

### New Capabilities

- `agent-tool-surface`: Evidence-led CLI/MCP task routing, typed public tool inventory, compatibility migration, and version-matched skill guidance after v0.5.

### Modified Capabilities

None. The change classifies and may version public adapters while preserving the underlying repository-navigation, freshness, graph, purpose, and administration behavior contracts.

## Impact

- `projectatlas-cli` command and MCP routers, tool schemas, runtime identity, task ownership, compatibility fixtures, generated host configuration, and installed-product E2E.
- The version-matched ProjectAtlas Codex plugin skill and any public documentation that recommends CLI or MCP routes.
- Windows, Linux, macOS x64, and macOS Apple Silicon installed workflows, including concurrent explicit-root routing.
- Issue #310 as the direct native sub-issue of release owner #493 and sole owner of this surface decision; #314 is blocked by #310 and #493 is blocked by both for final holistic acceptance.
